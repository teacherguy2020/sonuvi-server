diagnostics interface

Purpose

This page documents now-playing/diagnostics.html, the diagnostics and live-inspection console in the now-playing ecosystem.

This page is intentionally implementation-aware, because diagnostics.html is clearly not just a passive status screen. It acts as a multi-purpose operator console for:

  • making direct API requests
  • inspecting responses
  • testing endpoints with or without x-track-key
  • viewing live embedded UI surfaces side-by-side
  • navigating operational/debug workflows through a browser UI

Audio Info entry points and presentation

Audio Info is one capability with different client presentations, not one universal drawer:

  • Sonuvi iOS: open Audio Info from the native Audio Info entry associated

with Home audio details. The current product presentation is a dedicated screen/page, replacing the earlier native modal/drawer (confirmed by Brian on 2026-10-28). Navigate to that screen; do not restore drawer instructions. Exact native navigation implementation lives in the separate iOS repository and was not inspected for this Server documentation refinement.

  • Server tablet web controller: controller-tablet.html still has an

Audio info action (tabletAudioInfoBtn) opening audioInfoModal. That web modal exists in both indexed Server revisions, dee06724 and 4bf8889a; it must not be mistaken for the replaced native drawer.

  • Operator diagnostics: use the authenticated API/request console for the

endpoint below. Diagnostics is an inspection surface, not a replacement native Audio Info screen. There is no dedicated Server audio-info.html page in the reviewed main revision.

The native screen provides a separate navigation destination rather than a transient overlay; that presentation change does not create a new playback owner or change which measurements the Server can establish.

What Audio Info can establish

Evidence roleInterpretation
Source format / sourceFileEncoded media identity/codec/rate/bitrate; locally probed or provider-reported provenance matters
Decoded PCM / decodedAudioDecoder-reported sample representation; calculated PCM throughput is not encoded bitrate

Measured hardware outputCurrent ALSA endpoint parameters when exposed; not proof of every upstream conversion

These distinctions remain essential on the dedicated screen. ALSA format agreement alone does not establish end-to-end bit-perfect playback. The full Audio Info diagnostics contract below is the source of truth; preserve unavailable/unknown states rather than filling them with configured values.

Why this page matters

diagnostics.html appears to be one of the strongest operator-facing truth surfaces in the project.

It matters because it combines:

  • direct endpoint execution
  • live embedded views of multiple UI surfaces
  • clipboard/curl-oriented debugging helpers
  • quick comparison between API behavior and rendered UI behavior

That makes it extremely valuable when the question is:

  • what is the system doing right now?
  • what does the API say?
  • what does the rendered UI show?
  • do those things agree?

Observed logic:

  • if standalone=1, remain standalone
  • if top-level without standalone, redirect into:

- app.html?page=diagnostics.html

  • if embedded in another shell already, do not redirect

So diagnostics.html is designed for both:

  • standalone operator use
  • embedded/shell-hosted use inside the broader app

Qobuz Audio Info interpretation

The GET /config/moode/audio-info?view=rows surface is source-aware when Qobuz Connect owns the renderer. The Qobuz source format and decoded PCM are reported by the existing Pibuz/moOde get_qbzmeta cache. The hardware output is separate: Sonuvi reads ALSA playback hw_params/status files over the existing read-only moOde SSH path and reports Not measured when no open stream exposes parameters. It does not treat MPD being stopped as proof that the DAC is idle.

The endpoint labels the moOde audioinfo.php ALSA mode and audio chain as configured moOde/MPD path information, not verified Qobuz signal-path facts. MPD-only volume diagnostics are represented as unavailable for Qobuz, so raw Unknown MPD volume type or ALSA mixer-control errors do not leak into the Qobuz panel. The authenticated mobile audio-info contract forwards the safe audio object and optional diagnostics/provenance without exposing moOde URLs, file paths, PHP session identifiers, or renderer credentials.

Audio Info diagnostics contract

GET /config/moode/audio-info?view=rows&diagnostics=1 reuses the existing bounded, read-only ALSA probe on demand. It reads active playback hw_params/status from /proc/asound over the configured moOde SSH path; it does not open an ALSA device, seize playback, or restart a service. The legacy rows remain available and unchanged when diagnostics=1 is omitted.

The optional diagnostics object is versioned as audio-info.v1. The bearer GET /v1/mobile/audio-info route requests this view when Audio Info is opened and forwards the safe object alongside the existing rows. It is the shared Server/iOS diagnostic contract; native clients do not call the Track-Key /config route directly. Its main fields are:

  • sourceFormat: source-file or renderer-reported codec, bit depth, rate, and

channels;

  • decodedPcm: MPD/renderer-reported decoded format, not a DAC measurement;
  • configuredOutput: moOde's configured ALSA mode and chain, marked

valueType: "configured" and measured: false;

  • hardwareOutput: the current ALSA playback format, rate, channels, state,

and device label when procfs exposes them, marked valueType: "hardware-measured";

  • processing and volume: configured moOde/MPD state, never represented as

current hardware measurements;

  • conversion: deliberately status: "unknown", because ALSA endpoint

parameters cannot prove every conversion before the endpoint;

  • freshness: request-time capture and hardware-measurement timestamps.

The diagnostics object also has additive normalized fields for metadata accuracy:

  • sourceFile: container, codec, source bit depth, source sample rate,

channels, and encoded bitrate. codecStatus: "verified" means the bounded local-file ffprobe supplied the codec; reported means the value came from provider metadata, and unavailable means no codec evidence was available. Lossy codecs report bitDepthStatus: "not-applicable"; decoder precision is never copied into this object. Local files use the existing bounded ffprobe source probe when available, with stat-keyed cache invalidation.

  • decodedAudio: decoder-reported PCM precision, rate, and channels. Its

pcmBitrateBps is a nominal value calculated from those PCM parameters and is labeled pcmBitrateStatus: "calculated"; an encoded bitrate is not shown as decoded throughput.

  • output: the same actual ALSA observation as hardwareOutput, with device,

interface, format, rate, and channels grouped under the output role.

This distinction is required because moOde's audioinfo.php builds its Decoded to string from MPD's decoder fields but appends MPD's bitrate field to that same string. For AAC, moOde also maps MPD's floating-point precision marker (f) to a displayed 24-bit decoder value. Therefore a row such as PCM 24 bit 44.1 kHz, Stereo, 270 kbps means decoder-reported PCM parameters plus an encoded-source bitrate; it does not establish a 24-bit AAC source. The normalized fields keep those meanings separate. When diagnostics are requested and the verified source codec is lossy, the returned legacy Decoded to row omits the trailing encoded bitrate; the compatibility view without diagnostics remains unchanged.

The mobile response redacts local source paths and network URLs from legacy rows and never forwards the internal moOde URL, Track Key, or PHP session ID.

The main controller shells disable MPD transport/shuffle/repeat/seek controls while Qobuz owns playback; the server route also rejects those MPD commands with a source-aware unavailable response. No Qobuz remote-control API is implied by the metadata integration.
